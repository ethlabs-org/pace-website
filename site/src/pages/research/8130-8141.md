# EIP-8130 and EIP-8141: research notes

Research date: 2026-09-21. All spec facts come from the current `master` copies of the EIP files on eips.ethereum.org / github.com/ethereum/EIPs unless marked otherwise. Anything I could not confirm against a primary source is marked UNVERIFIED.

## 0. Short version

- EIP-8130 is now titled "Keystore Accounts" (renamed on 2026-09-03). Status: Draft. One author, Chris Hunter (Coinbase/Base). It is a new EIP-2718 transaction type plus an onchain Keystore system contract. Validation never runs wallet code; it runs a declared authenticator contract.
- EIP-8141 is "Frame Transaction". Status: Draft. Ten authors (Vitalik, lightclient, Felix Lange, Yoav Weiss, Alex Forshtat, Dror Tirosh, Shahaf Nacson, Derek Chiang, Toni Wahrstätter, Stavros Vlachakis). Transaction type `0x06`. A transaction is a list of frames; VERIFY frames run arbitrary EVM under mempool constraints.
- 8141 was moved to Scheduled for Inclusion (SFI) for Hegotá on ACDE #244 (2026-08-27). The EF Protocol tier list (2026-09-07) calls it one of two "must-ship" S-tier EIPs, with EIP-7805 FOCIL. Hegotá is the fork after Glamsterdam, expected 2027.
- The two specs do not reference each other. The 8130 spec has no mention of 8141 and vice versa.
- Base and Ethereum tried to reconcile the two (8130 as a structured profile over 8141 frames) and gave up in the week before 2026-09-15 (The Block, Unchained). Base ships 8130 in its Cobalt upgrade; L1 ships 8141.
- Only ethrex (LambdaClass) runs a public 8141 network today. Nethermind has an open PR. Erigon opened a tracking issue on 2026-09-18. Geth, Reth, Besu: no public implementation found (UNVERIFIED).

## 1. EIP-8130: Keystore Accounts

### Metadata

- Title: `Keystore Accounts` (the old title "Account Abstraction by Account Configuration" still appears in the discussion-thread URL, search snippets and many third-party articles).
- Status: Draft, Standards Track: Core.
- Author: Chris Hunter (@chunter-cb), chris.hunter@coinbase.com.
- Created: 2025-10-14.
- Discussions-to: https://ethereum-magicians.org/t/eip-8130-account-abstraction-by-account-configurations/25952 (thread opened 2025-10-24).
- Requires: EIP-170, EIP-2718, EIP-7623.
- Recent commits to `EIPS/eip-8130.md`: 2026-08-19 (adoption profiles, bounded auth gas, timestamp normalisation), 2026-08-27 (remove `CONTRACT_ESTABLISHED` flag), 2026-09-03 (rename to Keystore Accounts), 2026-09-14 (align scope bits, `POLICY`/`OPERATOR` semantics and `importAccount` with the canonical repo), 2026-09-16 (apply EIP-7623 calldata floor to intrinsic gas). So the last update is 2026-09-16.
- Companion drafts: ERC-8168 "8130 Payer Service Capability" (Draft) and EIP-8140 "Token Gas Payments for EIP-8130" (Draft). Authors and dates of these two: UNVERIFIED (eip.tools pages did not render the body).
- Reference implementation: https://github.com/base/eip-8130 (README says "active work in progress ... not audited").

### Account model

Every account (EOA or contract) has a row in the Keystore. An account authorises a set of "actors". An actor is a 32-byte `actorId` that an authenticator derives from key material. Each actor has an authenticator address, an expiry, a scope bitmask, and optionally a policy commitment and policy manager. Validation reads this state directly. Nodes only run the declared authenticator (a STATICCALL with a known gas bound). Wallet code never runs during validation.

Existing EOAs need no registration. The "self-actor" is `actorId == bytes32(uint256(uint160(account)))`, resolved from an inline default-EOA config in the packed account-state slot. So any EOA can send an 8130 transaction immediately with a plain secp256k1 signature. `DEFAULT_EOA_REVOKED` turns that off.

Already-deployed contract accounts (for example ERC-4337 wallets) call `importAccount()` on the Keystore themselves, one time.

### Keystore contract and storage layout

Keystore is at `KEYSTORE_ADDRESS`, deployed by deterministic CREATE2 so the address is the same on every chain. Exact address value: not stated in the EIP text (UNVERIFIED; "see canonical repository").

Per-actor `actor_config` slot is normatively packed:

```
authenticator(20) ‖ expiry(6) ‖ scope(2) ‖ reserved(4)
```

`expiry` is a `uint48` Unix time in seconds, 0 = never. `scope` is `uint16`. Actors with a policy get two more slots: `policy_commitment(account, actorId) -> bytes32` and `policy_manager(account, actorId) -> address`.

Per-account state slot holds: lock flags (`LOCKED`, `UNLOCK_INITIATED`), `unlock_delay` (uint16 seconds, max about 18.2 hours), `local_epoch`, `local_sequence`, `multichain_sequence`, and the inline self-actor config.

### Key types (canonical authenticator set)

| Name | Algorithm | Authenticator | actorId derivation |
|---|---|---|---|
| `k1` | secp256k1 | `K1_AUTHENTICATOR` = native sentinel `address(1)` | `bytes32(uint256(uint160(recovered_address)))` |
| `p256` | P-256 raw | onchain `P256Authenticator` | `keccak256(abi.encodePacked(x, y))` |
| `passkey` | WebAuthn / FIDO2 | onchain `WebAuthnAuthenticator` | `keccak256(abi.encodePacked(x, y))` |
| `delegate` | one account acts for another | onchain `DelegateAuthenticator` | `bytes32(uint256(uint160(delegated_address)))` |

Delegate depth is 1; the nested authenticator must itself be canonical. Non-canonical authenticators can be registered and used in normal EVM flows (ERC-1271 etc.); whether they are accepted on the 8130 transaction path depends on the chain's adoption profile. Two profiles: "L1 profile (normative schedule, permissive acceptance)" and "L2 profile (configurable schedule, canonical-only path)". A chain MUST declare which profile it activates.

Authenticator interface:

```solidity
function authenticate(bytes32 hash, bytes calldata data) external returns (bytes32 actorId)
```

### Interfaces (exact spellings from the spec)

Keystore functions:

- `importAccount()`
- `confirmKeystoreImport() external view returns (bytes32 digest, InitialActor[] memory initialActors)` (called on the account being imported)
- `authorizeActor(bytes32 actorId, ActorConfig config, bytes policyData)`
- `revokeActor(bytes32 actorId)`
- `applySignedAccountChanges(SignedAccountChanges changes)`
- `createAccount(bytes32 userSalt, bytes code, InitialActor[] initialActors)`
- `authenticateActor(address account, bytes32 hash, bytes auth) external returns (bytes32 actorId, uint16 scope)`
- `validateSignature(address account, bytes32 hash, bytes auth) external returns (bytes32 actorId, uint16 scope)`
- `isValidSignature(bytes32 hash, bytes signature) external returns (bytes4)` (ERC-1271, on the account)
- `getActorConfig(address account, bytes32 actorId) external view returns (ActorConfig)`
- `getActorWithPolicy(address account, bytes32 actorId) external view returns (ActorConfig config, address manager, bytes32 commitment)`
- `getPolicyCommitment(address account, bytes32 actorId) external view returns (bytes32)`
- `getNonce(address account, uint256 nonce_key) external view returns (uint64)` (Nonce Manager)

Transaction-context getters (a `TX_CONTEXT_ADDRESS` system contract): `getTransactionSender()`, `getTransactionPayer()`, `getTransactionCalls() returns (Call[][])`, `getTransactionGasLimit()`, `getTransactionSenderActorId()`.

Events:

- `ActorAuthorized(address indexed account, bytes32 indexed actorId, bytes32 actorData)` (one fetch rendered the third param as `bytes actorData`; the raw markdown says `bytes32`. Treat the type as UNVERIFIED, the name is right.)
- `ActorRevoked(address indexed account, bytes32 indexed actorId)`
- `AccountLocked(address indexed account, uint16 unlockDelay)`
- `AccountUnlockInitiated(address indexed account, uint256 unlocksAt)`
- `DelegationApplied(address indexed account, address indexed target)`

Error: `ActorPolicyViolation(bytes32 actorId, address target)`.

### Transaction fields

`AA_TX_TYPE` transaction, RLP fields in order: `chain_id, sender, nonce_key, nonce_sequence, valid_after, valid_before, max_priority_fee_per_gas, max_fee_per_gas, gas_limit, account_changes, calls, metadata, payer, sender_auth, payer_auth`.

Type byte: third-party sources (cryptobriefing, eip8130.com summaries) say `AA_TX_TYPE = 0x79`, and the spec defines `REPLAY_ID_TYPE = 0x7901`, which is consistent. The spec text itself does not print the value in the fetched render. Mark `0x79` as LIKELY but UNVERIFIED against the spec. The magicians thread (2026-07-06) discussed changing the type number to avoid OP-Stack collisions, so it may move.

`valid_after` / `valid_before` are Unix timestamps; values above `TIMESTAMP_MS_THRESHOLD = 10^11` are read as milliseconds. Validity: `valid_after <= block.timestamp*1000 <= valid_before`.

### Nonce model (parallel / 2D)

A Nonce Manager precompile at `NONCE_MANAGER_ADDRESS` keeps `(nonce_key, nonce_sequence)`:

| `nonce_key` | Behaviour |
|---|---|
| `0` | standard sequential nonce |
| `1 .. NONCE_KEY_MAX-1` | independent parallel channels, each sequential |
| `NONCE_KEY_MAX` | nonce-free mode |

Nonce-free mode: `nonce_sequence` must be 0, `valid_before` must be set, and replay protection is a `replay_id = keccak256(REPLAY_ID_TYPE || rlp([chain_id, resolved_sender, valid_after, valid_before, account_changes, calls, metadata, payer]))` kept in a fixed-size circular buffer (`REPLAY_BUFFER_CAPACITY = peak_nonce_free_throughput * NONCE_FREE_EXPIRY_WINDOW`, both chain parameters). Fees and signatures are excluded from the id, so a fee bump does not create a new id.

Actor nonce rights: admin (`scope == 0x00`) may use any key; a restricted actor without the `NONCE` bit may only use nonce-free mode; with the `NONCE` bit it gets the full 2D space.

Numeric `NONCE_KEY_MAX`: UNVERIFIED (spec defers to canonical repo).

Gas: first use of a standard nonce key costs 22,100, existing key 5,000, nonce-free 13,000. `AA_BASE_COST` = 15,000. `MAX_AUTHENTICATION_GAS` = 100,000 (suggested).

### Signature validation

Sender signs `keccak256(AA_TX_TYPE || rlp([chain_id, sender, nonce_key, nonce_sequence, valid_after, valid_before, max_priority_fee_per_gas, max_fee_per_gas, gas_limit, account_changes, calls, metadata, payer]))`. Payer signs the same fields with `AA_PAYER_TYPE` as the domain byte.

`sender_auth` format: if `sender` is empty, raw 65-byte `r||s||v` and ecrecover gives the sender. If `sender` is set, `authenticator(20) || data`; for `K1_AUTHENTICATOR` data is `r||s||v`, other authenticators define their own. The node runs `authenticateActor(account, hash, auth) -> (actorId, scope)`: one SLOAD for the config plus one STATICCALL to the authenticator. Then it checks expiry and scope.

### Scope bits (sessions, scoped keys)

`scope` is a `uint16`; `0x00` means admin (unrestricted).

| Bit | Name | Meaning |
|---|---|---|
| `0x01` | `OPERATOR` | may originate transactions to any `call.to` |
| `0x02` | `SELF_PAYER` | may pay gas when `payer == sender` |
| `0x04` | `SPONSOR_PAYER` | may act as `payer_auth` for another sender |
| `0x08` | `POLICY` | gated: every `call.to` must equal the actor's `policy_manager` |
| `0x10` | `NONCE` | restricted actor may use sequenced nonce keys |

A policy-bearing actor "may call exactly one target: its configured `manager`". The manager contract reads the actor's `commitment` via `getPolicyCommitment` / `getActorWithPolicy` and enforces app rules. The spec's example: "A subscription session key limited to 5 USDC per 30-day period with a two-target allowlist." `manager = account` means the account's own code enforces the policy. `OPERATOR | POLICY` is ungated; policy keys must not carry `OPERATOR`. The gate target is snapshotted once at the start of `calls`.

Expiry: live iff `expiry == 0 || block.timestamp <= expiry`. An expired actor still occupies its slot until `revokeActor`.

### Batch execution

`calls` is a list of phases; each phase is a list of calls. A phase is atomic (all-or-nothing). Phases commit independently: a revert in phase 1 does not undo phase 0. One `gas_limit` pool for all phases. Every call runs with `msg.sender == tx.origin == sender` and `value = 0` (calls carry no ETH; the eip8141.io comparison lists this as a limitation).

### Account changes

`account_changes` entries: `0x00` Create (CREATE2 from the Keystore with `effective_salt = keccak256(user_salt || actors_commitment)`), `0x01` Config change (signed batch: `AuthorizeActor`, `RevokeActor`, `IncrementLocalEpoch`, `Lock`, `Unlock`), `0x02` Delegation (sets EIP-7702 code delegation, admin self-actor only; replaces the 7702 authorization list).

Config changes travel on two channels: multichain (plain monotonic counter, valid on any chain, `chain_id = 0` in the signed payload) and local (`local_epoch || local_sequence`, with an `UNSEQUENCED` = `uint32` max value for just-in-time unsequenced grants that consume no counter).

### Explicit relation to EIP-8141

None in the spec. The text does not mention 8141. See section 4 for what people said outside the spec.

## 2. EIP-8141: Frame Transaction

### Metadata

- Title: `Frame Transaction` (singular in the spec; press says "Frame Transactions").
- Status: Draft, Standards Track: Core.
- Authors: Vitalik Buterin (@vbuterin), lightclient (@lightclient), Felix Lange (@fjl), Yoav Weiss (@yoavw), Alex Forshtat (@forshtat), Dror Tirosh (@drortirosh), Shahaf Nacson (@shahafn), Derek Chiang (@derekchiang), Toni Wahrstätter (@nerolation), Stavros Vlachakis (@svlachakis).
- Created: 2026-01-29.
- Discussions-to: https://ethereum-magicians.org/t/frame-transaction/27617.
- Requires: 1559, 2718, 2780, 3529, 3607, 4844, 7594, 7623, 7702, 7708, 7778, 7825, 8037.
- Recent commits: 2026-08-18 (relax banned opcodes; add `SIGDATACOPY`), 2026-08-20 (charge resolved target access at frame entry; APPROVE failure scoping; precompile dispatch), 2026-08-21 (calldata floor per EIP-7976 token count), 2026-08-24 (block execution gas before refund, EIP-7778), 2026-09-01 (remove redundant state gas check). Last update 2026-09-01.

### Transaction type and structure

`FRAME_TX_TYPE = 0x06`. Payload:

```
[chain_id, nonce, sender, frames, signatures, fees, blob_versioned_hashes]
frames     = [[mode, flags, target, limits, value, data], ...]
limits     = [execution, state]
signatures = [[scheme, signer, msg, signature], ...]
fees       = [max_priority_fee_per_gas, max_fee_per_gas, max_fee_per_blob_gas]
```

Constants: `FRAME_TX_INTRINSIC_COST = 12000`, `FRAME_TX_PER_FRAME_COST = 475`, `ENTRY_POINT = address(0xaa)`, `EXPIRY_VERIFIER = address(0x8141)`, `EXPIRY_DATA_LENGTH = 8`, `MAX_FRAMES = 64`, `MAX_VERIFY_GAS = 100000`, `MAX_VERIFY_STATE_GAS = 500000`, `MAX_PENDING_TXS_USING_NON_CANONICAL_PAYMASTER = 1`.

Each frame carries its own execution and state gas budget (state gas per EIP-8037). Budgets do not roll over.

### Frame modes

- `DEFAULT (0)`: runs with `ENTRY_POINT` as caller.
- `VERIFY (1)`: validation. Runs like a static call; failure invalidates the whole transaction.
- `SENDER (2)`: runs as the sender; needs prior execution approval.

Approval is the `APPROVE` opcode (`0xaa`) with scopes `APPROVE_NONE (0x0)`, `APPROVE_PAYMENT (0x1)`, `APPROVE_EXECUTION (0x2)`, `APPROVE_EXECUTION_AND_PAYMENT (0x3)`. Only the frame's `resolved_target` may call it. Repeated approvals revert.

Introspection opcodes: `TXPARAM (0xb0)`, `FRAMEDATALOAD (0xb1)`, `FRAMEDATACOPY (0xb2)`, `FRAMEPARAM (0xb3)`, `SIGPARAM (0xb4)`, `SIGDATACOPY (0xb5)`.

Signature schemes: `SECP256K1 (0x1)` 65 bytes, 2800 gas; `P256 (0x2)` 128 bytes `r||s||qx||qy`, 6700 gas; `ARBITRARY (0x0)` raw bytes, 100 gas, readable via `SIGDATACOPY`. Signatures are verified before any frame executes.

Accounts without code get "default code": in VERIFY it validates signatures and approves; in SENDER/DEFAULT it returns success.

### Validation prefix vs execution

The validation prefix is the shortest frame prefix that sets the payer. Once `payer` is set "subsequent frames are outside public mempool validation and may be arbitrary".

Recognised prefix patterns for the public mempool: `self_verify`; `deploy, self_verify`; `only_verify, pay`; `deploy, only_verify, pay`. Optional expiry verifier frame must be frame 0. Non-canonical paymasters get one pending tx at a time; canonical paymasters are code-matched and track reserved balances.

Mempool rules for the prefix: total gas of the prefix plus signature checks at most `MAX_VERIFY_GAS`; state gas at most `MAX_VERIFY_STATE_GAS`; banned opcodes in VERIFY include `GASPRICE`, `BLOCKHASH`, `TIMESTAMP` (except in the expiry verifier), `NUMBER`, `PREVRANDAO`, `GASLIMIT`, `BASEFEE`, `BLOBBASEFEE`, `GAS` (except before CALL), `CREATE`/`CREATE2` and `SETDELEGATE` (except in a deploy frame), `BALANCE`, `SELFBALANCE`, `SSTORE` (except sender storage in deploy), `SLOAD` on non-sender storage, `SELFDESTRUCT`, `INVALID`. No atomic batch flag in the prefix.

### Nonce

Single account nonce: "Ensure `tx.nonce == state[tx.sender].nonce`". The nonce is consumed at payment approval. Mempool intake does not consume it. Two pending txs with the same nonce are replacements. The base spec has no parallel nonces.

Parallel nonces live in a separate EIP: EIP-8250 "Keyed Nonces for Frame Transactions" (Draft, created 2026-04-16, authors Thomas Thiery, Toni Wahrstätter, lightclient, Vitalik Buterin; requires 7623, 8037, 8141). It replaces `nonce` with `nonce_keys` (list of uint256) and `nonce_seq` (uint64). `nonce_keys == [0]` aliases the legacy nonce; non-zero keys are sequences in a `NONCE_MANAGER` system contract at `0x...8250`. Mempool identity becomes `(sender, nonce_keys, nonce_seq)` but the one-pending-frame-tx-per-sender limit stays ("does not by itself change EIP-8141's public-mempool guidance"; "future keyed-aware mempools" are left open).

Related: EIP-8272 "Recent Roots for Frame Transactions" (Draft, created 2026-05-15, authors Thomas Thiery, Vitalik Buterin, Toni Wahrstätter, lightclient; requires 7843, 8141). A canonical VERIFY frame that checks up to 16 `(source_id, slot, root)` tuples, aimed at privacy pools.

### Batching

`ATOMIC_BATCH_FLAG = 0x4`. Frames with the flag batch with their successor; a failed frame rolls back the whole batch's state. Approval must precede a batch.

## 4. Building an 8130 account on top of 8141: what is known and what is open

### What was attempted

- March 2026 breakout #2 (2026-03-25): Chris Hunter said "8130 cannot be implemented on 8141 in its current form due to delegation limitations" (he meant Keystore-style delegation, which is unrelated to 7702). Others liked that 8130 lets anyone deploy validation logic as a contract.
- Aug 13 ACDE: client teams agreed to compare 8141 and 8130 in a breakout on 2026-08-25. On ACDE #244 (2026-08-27) Derek Chiang laid out "updating Frame to resemble EIP-8130 versus the reverse"; Chris (Base) left the call before the decision, noting "Moving to the frame model does... cost stuff for us". 8141 was SFI'd.
- Sept 7: Chiang's post said 8130 "could place defined structures over frames": an onchain keystore where accounts register authenticators, so nodes can identify validation requirements before running wallet code, while keeping frames' flexibility. The Block and Unchained (2026-09-15) report that the joint effort ended the week before. Chiang: "they all required one side or the other to compromise at least a little bit on their core goals."
- lightclient's "Frames Are All You Need" note lists three things 8130 does differently: nonce and config in system contracts instead of the account; verifier access limits that "preclude trustless withdrawals from privacy protocols"; hardcoded payer signatures that prevent "trustless sponsorship". Date of the note: UNVERIFIED.
- eip8141.io/eip-8130 (an 8141-side comparison page, author UNVERIFIED) summarises the mapping: 8130 validation is one SLOAD plus one STATICCALL to a declared authenticator, versus 8141's arbitrary EVM in VERIFY frames bounded by behavioural rules. It lists what 8130 has that base 8141 lacks: call phases, explicit `payer`/`payer_auth` fields, `account_changes` (create, config, 7702 delegation in one tx), and `chain_id = 0` multichain config replays.

### How an 8130-style account would map onto 8141 (my reading; no spec covers this)

- Keystore: deploy the Keystore as an ordinary contract (the 8130 spec already says that on non-8130 chains the Keystore is "available as standard contract"). The account's VERIFY frame calls `authenticateActor(account, hash, auth)` on it, checks scope and expiry, then `APPROVE(APPROVE_EXECUTION_AND_PAYMENT)`. This fits the `self_verify` pattern. Every sender must have code though; a bare EOA gets 8141's default code, which only does the built-in signature check, so the EOA-with-no-registration property of 8130 turns into "delegate to a Keystore-aware account code first" (via 7702 or a deploy frame).
- Authenticators: `K1` and `P256` map onto 8141's native `SECP256K1`/`P256` signature entries in `signatures`; WebAuthn and delegate authenticators would use `ARBITRARY` signatures read back with `SIGDATACOPY` and verified in the VERIFY frame. The gas for WebAuthn parsing has to fit inside `MAX_VERIFY_GAS = 100000` together with the Keystore SLOADs.
- Mempool: 8141's VERIFY rules allow `SLOAD` only on sender storage. The Keystore is a separate contract, so reading `actor_config` from it in a VERIFY frame breaks the current banned-opcode list. Either the Keystore must get a carve-out (like `EXPIRY_VERIFIER` and canonical paymasters have), or config has to be mirrored into sender storage. This is the biggest concrete gap and it is exactly the "structural vs behavioural mempool safety" split the comparison page describes. Not addressed in any spec. OPEN.
- Payer: 8130's `payer`/`payer_auth` become an `only_verify, pay` prefix with a canonical paymaster contract. Non-canonical sponsors are limited to one pending tx each, which is much tighter than 8130's `SPONSOR_PAYER` scope. OPEN whether 8130-style high-rate payers can be made "canonical" under 8141.
- Batch execution: 8130 phases map to SENDER frames with `ATOMIC_BATCH_FLAG` grouping; per-phase independence is natural in 8141 because frames commit separately. 8141 frames can carry `value`; 8130 calls cannot, so the 8141 version is a superset here.
- Policy-gated keys (`POLICY` scope, single `policy_manager` target): enforced in the account's SENDER frame or at APPROVE time by checking each call target, since 8141 has no protocol-level gate. It works, but the check then lives in wallet code with no protocol rule behind it.

### Open questions

1. Parallel nonces. Base 8141 has one nonce per sender and one pending tx per sender in the mempool. EIP-8250 adds keyed nonces but explicitly keeps the one-pending-per-sender rule, so 8130's "concurrent channels" property does not carry over to the public mempool until a "keyed-aware mempool" rule is written. 8130's nonce-free mode (`NONCE_KEY_MAX` + replay buffer) has no 8141 equivalent at all; the closest is the expiry verifier frame plus an in-account replay set, which costs state gas. OPEN.
2. 8250 is A-tier and has no SFI decision. If Hegotá ships 8141 without 8250, an 8130-on-8141 account has a single sequential nonce.
3. Cross-contract SLOAD in VERIFY (Keystore reads). Needs a spec change or a canonical-contract exemption. OPEN.
4. Delegation depth. Chris Hunter's March objection about "delegation limitations" (one account acting for another via the delegate authenticator) is unresolved in public notes. OPEN.
5. Multichain config changes (`chain_id = 0` batches) need the Keystore to exist at the same CREATE2 address on L1; nothing in 8141 provides that, so it is a deployment question and needs no protocol change.
6. Payer model. 8141 canonical paymasters are code-matched; 8130's permissionless "any contract can pay" is not expressible under current 8141 mempool rules beyond the one-pending limit.
7. Whether 8141's spec will still change. SFI came "with the caveat that its specification may still change", and there were spec commits as late as 2026-09-01.
8. Wallet fragmentation. Base ships 8130 (`0x79`, UNVERIFIED) on Cobalt in September 2026; L1 ships `0x06` frames in 2027. A wallet targeting both chains needs both encoders. The 8130 spec's own answer for non-8130 chains is ERC-4337 transport; it does not mention 8141.
