# ERC-7710 and ERC-7715: state of the standards, what ships, and what a native account would need

Research date: 2026-09-21. Every claim below comes from the latest version of the linked source unless marked UNVERIFIED.

## 1. ERC-7710: Smart Contract Delegation

**Front matter.** Status: Draft. Created 2024-05-20. Authors: Ryan McPeck (@McOso), Dan Finlay (@DanFinlay), Rob Dawson (@rojotek), Derek Chiang (@derekchiang). Requires ERC-1271 and ERC-7579. Discussion thread: ethereum-magicians.org/t/16690. Last change to the spec file in ethereum/ERCs: 2025-06-10 ("Improved ERC in response to feedback on ethereum magicians", Dan Finlay). Before that: 2024-12-12 (initial merge).

**What the ERC actually standardises.** Almost nothing on the account side. It defines one contract role, the Delegation Manager, and one function on it:

```solidity
interface ERC7710Manager {
    function redeemDelegations(
        bytes[] calldata _permissionContexts,
        bytes32[] calldata _modes,
        bytes[] calldata _executionCallData
    ) external;
}
```

The three arrays are processed as tuples, atomically. `_permissionContexts[i]` is an opaque proof of authority (the ERC does not fix its encoding). `_modes[i]` is an ERC-7579 execution mode (single call, batch, delegatecall, and so on). `_executionCallData[i]` is ERC-7579-encoded execution data (target, value, callData for single; packed array for batch).

Things the ERC does NOT define: a Delegation struct, a Caveat struct, a caveat enforcer interface, how a delegator signs, or any interface the delegator account must implement. The text says this was deliberate: "we decided to remove the requirement for the delegator to implement any specific interface." The manager is responsible for knowing how to call the delegator; the delegator only issues permission contexts for managers it trusts. The ERC points to `Example7710Manager.sol` in its assets and to the MetaMask Delegation Framework as the full reference.

**Flow (per the ERC).**
1. A delegator (the user's account) produces a permission context off-chain and gives it to a delegate.
2. The delegate calls `redeemDelegations` on the Delegation Manager with the context, a mode, and execution calldata.
3. The manager validates the context (signature, revocation, caveats) and then calls into the delegator account to run the execution.
4. Security section: the app must simulate `redeemDelegations` before sending, because a delegation can expire, be revoked, or be invalidated by state changes between simulation and inclusion.

**What the reference implementation (MetaMask delegation-framework) adds.** Since the ERC is thin, the de facto interface is MetaMask's. From `src/utils/Types.sol`:

```solidity
struct Delegation {
    address delegate;     // who may redeem
    address delegator;    // the account granting authority
    bytes32 authority;    // ROOT_AUTHORITY or hash of the parent delegation
    Caveat[] caveats;
    uint256 salt;
    bytes signature;      // EIP-712 signature by delegator
}
struct Caveat {
    address enforcer;     // a contract implementing ICaveatEnforcer
    bytes terms;          // set by the delegator
    bytes args;           // set by the redeemer at call time
}
```

`DelegationManager.redeemDelegations(bytes[] _permissionContexts, ModeCode[] _modes, bytes[] _executionCallDatas)` decodes each context as `abi.decode(ctx, (Delegation[]))`. The array is leaf first: `delegations[0].delegate` must be `msg.sender` (or `ANY_DELEGATE`), each `authority` must equal the hash of the next delegation, and the last one must have `authority == ROOT_AUTHORITY` (`0xff..ff`). An empty array means the caller is executing for itself. Signatures are checked with `ECDSA.recover` over the EIP-712 typed hash for EOA delegators and with `IERC1271(delegator).isValidSignature(hash, sig)` for contract delegators.

Caveat enforcers (`ICaveatEnforcer`) get four hooks, all with the same parameters `(terms, args, mode, executionCalldata, delegationHash, delegator, redeemer)`: `beforeAllHook`, `beforeHook`, `afterHook`, `afterAllHook`. Order at redemption: beforeAll for every caveat, before for every caveat, execute, after (reverse), afterAll (reverse). Any revert aborts the whole redemption.

**How an account plugs in.** The manager invokes the root delegator with:

```solidity
IDeleGatorCore(rootDelegator).executeFromExecutor(mode, executionCalldata);
```

`IDeleGatorCore is IERC1271` and has exactly one extra function, `executeFromExecutor(ModeCode, bytes) payable returns (bytes[])`, the ERC-7579 executor entry point. So a wallet that wants to be a 7710 delegator with this manager needs two things: an `isValidSignature` that accepts the delegator's EIP-712 delegation signature, and an `executeFromExecutor` that trusts the DelegationManager address as an executor module. MetaMask ships three account implementations (Hybrid, MultiSig, Stateless7702) that do this. UNVERIFIED: the exact current list of caveat enforcers (the docs page for delegations returned 404 during this research).

## 2. ERC-7715: Request Permissions from Wallets

**Front matter.** Status: Draft. Created 2024-05-24. Authors: Luka Isailovic, Derek Rein, Dan Finlay, Derek Chiang, Fil Makarov, Pedro Gomes, Conner Swenberg, Lukas Rosario, Idris Bowman, Jeff Smale. Requires EIP-4337 and ERC-7710. Discussion: ethereum-magicians.org/t/20100. Spec file history in ethereum/ERCs: 2025-02-18 initial merge (Pedro Gomes), 2025-02-20 diagram swap, 2026-01-16 "Simplify specification to ease wallet implementation" (Idris Bowman, MetaMask).

**Important: the January 2026 rewrite changed the method name and shape.** Most third-party write-ups (Eco, Medium, Reown's 2024 blog) still describe the old version. Both versions are summarised here because production code targets one or the other.

### 2a. Current spec (since 2026-01-16)

Methods:
- `wallet_requestExecutionPermissions`
- `wallet_revokeExecutionPermission`
- `wallet_getSupportedExecutionPermissions`
- `wallet_getGrantedExecutionPermissions`

Request: an array of

```ts
type PermissionRequest = {
  chainId: Hex;                  // EIP-155, hex uint256
  from?: Address;                // user account (optional)
  to: Address;                   // the dapp's session account that will redeem
  permission: {
    type: string;                // e.g. "native-token-allowance"
    isAdjustmentAllowed: boolean;
    data: Record<string, any>;
  };
  rules?: { type: string; data: Record<string, any> }[];
};
```

Response: the same object plus

```ts
{
  context: Hex;                      // opaque; passed to redeemDelegations
  dependencies: { factory: Hex; factoryData: Hex }[];  // accounts that must be deployed first
  delegationManager: Address;        // the ERC-7710 manager to call
}
```

The wallet may return different values than requested; "it is not guaranteed that the values received are equivalent to those requested." `isAdjustmentAllowed` says whether the wallet may attenuate (the text says "reduce or increase") the permission to fit what the user approves.

Defined types: only `native-token-allowance` (`data.allowance`, hex) is specified in full. `erc20-token-allowance` and `erc721-token-allowance` appear as examples. One rule type is defined: `expiry` with `data.timestamp`. The ERC says explicitly that it does not give an exhaustive list and expects other ERCs to add types.

There is no `signer` object anymore. The session account address is just `to`. There is no `accountMeta` / `signerMeta`; those collapsed into `dependencies` and `delegationManager`.

Pairing with 7710: redemption is spelled out as `sendTransaction({ to: delegationManager, data: redeemDelegations([context], [executionMode], [encodedAction]) })`. So 7715 is the off-chain half (how a dapp asks and what it gets back) and 7710 is the on-chain half (how the returned `context` is spent).

`wallet_revokeExecutionPermission` takes `{ permissionContext }` and returns empty. `wallet_getSupportedExecutionPermissions` returns `Record<permissionType, { chainIds: Hex[]; ruleTypes: string[] }>`.

### 2b. Old spec (Feb 2025 to Jan 2026, still what many SDKs implement)

Method `wallet_grantPermissions`. Request fields: `chainId`, `address?`, `expiry` (top-level unix timestamp), `signer`, `permissions[]`, `policies[]`. Signer types: `wallet` (the wallet itself signs), `key` (`{type: KeyType, publicKey}`), `keys` (multisig array), `account` (`{address}`, the ERC-7710 route). Permission types: `native-token-transfer`, `erc20-token-transfer`, `erc721-token-transfer`, `erc1155-token-transfer`, `gas-limit`, `call-limit`, `rate-limit`. Response: `context`, `accountMeta?` (factory, factoryData), `signerMeta` with `userOpBuilder` (ERC-7679) for key signers or `delegationManager` for the account signer. This is the version Reown Smart Sessions and the Eco articles describe.

### 2c. Thread state

The Magicians thread (May 2024 to April 2026) shows the simplification came from MetaMask's implementation pain (June 2025 post, then the PR). Open issues raised: how a wallet pins a dapp identity across requests, dynamic permission updates for volatile assets, and (April 2026) the risk of permissions that only constrain a 4-byte selector without binding the target contract and calldata. No move toward Review or Last Call as of today.

## 3. Production status

### MetaMask (the only full 7715 + 7710 wallet in production)

- Product names: MetaMask Smart Accounts Kit (formerly Delegation Toolkit), MetaMask Delegation Framework (the contracts; accounts are called DeleGators), and the user-facing feature "Advanced Permissions".
- Launch: metamask.io news post dated 2026-04-06, "Advanced Permissions ... is now live". Requires MetaMask v13.23.0 or later (earlier docs said Flask 13.5.0, now stable). The support article says the feature relies on MetaMask’s Smart Accounts, that they are on by default, and that MetaMask prompts an EOA to upgrade (EIP-7702) when a permission is requested. Users manage grants under "Dapp connections".
- Standards fidelity: the RPC method is `wallet_requestExecutionPermissions` (the new name) and the response carries `context` and `delegationManager`, so the on-chain half is exactly 7710. Two variants from the ERC text: MetaMask puts `expiry` as a required top-level number on each request (the ERC puts it in `rules[{type:"expiry"}]`), and the MetaMask permission types are its own set, wider than the ERC's `native-token-allowance` example. The concept page also still says the method "requires a signer parameter"; the reference page and guides use `to`. Treat the reference page as current.
- Permission types the SDK ships: `native-token-allowance`, `native-token-periodic`, `native-token-stream`, `erc20-token-allowance`, `erc20-token-periodic`, `erc20-token-stream`. Fields: allowance types take `allowanceAmount`, `startTime`, `justification` (+ `tokenAddress` for ERC-20); periodic takes `periodAmount`, `periodDuration`, `startTime`; stream takes `amountPerSecond`, `initialAmount`, `maxAmount`, `startTime`. The April 2026 announcement also lists a third category, "Revocation: allows a dapp to revoke ERC-20 token approvals on the user's behalf". UNVERIFIED: its exact type string (the docs page 404'd).
- Redemption on the dapp side: the session account is either a contract account (bundler client extended with `erc7710BundlerActions`, calling `sendUserOperationWithDelegation({ permissionsContext, delegationManager, calls })`) or an EOA (wallet client extended with `erc7710WalletActions`, `sendTransactionWithDelegation`). Both end in `DelegationManager.redeemDelegations`.
- Chains for Advanced Permissions (docs "Supported networks" page): mainnet Arbitrum Nova, Arbitrum One, Base, Berachain, BNB Chain, Citrea, Ethereum, Gnosis, Linea, Monad, Optimism, Polygon, Sei, Sonic, Unichain, plus 15 testnets. The April announcement listed 12; the docs list 15 today. Delegation without 7715 (direct SDK use) is on 23 mainnets. Constraint: only chains with EIP-7702, because the MetaMask user's account is a 7702-delegated EOA.
- Where the wallet-side logic lives: the Magicians thread references MetaMask's `snap-7715-permissions` repository, i.e. the permission UI and delegation signing run inside a Snap. UNVERIFIED whether that is still the architecture in the shipped v13.23 build.

### Others

- Coinbase Smart Wallet: ships "Spend Permissions" (`SpendPermissionManager` at `0xf85210B21cC50302F477BA56686d2019dC9b67Ad` on Arbitrum, Avalanche, Base, Ethereum, Optimism, Polygon). The manager is added as an owner of the wallet; permissions are periodic native/ERC-20 allowances. The CDP docs do not mention ERC-7715 or 7710 at all; the API is SDK-specific (`useCreateSpendPermission`, `cdp.evm.createSpendPermission`). Third-party articles claiming Coinbase "added support for wallet_grantPermissions" could not be confirmed against Coinbase's own docs. Treat it as the same idea implemented outside the standard.
- Reown (WalletConnect) AppKit Smart Sessions: `@reown/appkit-experimental/smart-session`, early access since September 2024, targets the OLD `wallet_grantPermissions` shape with `key`/`keys` signers and a userOp-builder + cosigner model, "currently compatible with Smart Accounts" (their embedded contract account). No evidence it has been updated to `wallet_requestExecutionPermissions`. UNVERIFIED whether any external wallet answers these requests over WalletConnect today.
- Rhinestone / Biconomy SmartSessions (`erc7579/smartsessions`): an ERC-7579 validator module for session keys usable with Safe (via the 7579 adapter), Kernel, and Nexus. It is the enforcement layer that a wallet could put behind a 7715 `key` signer. It is not itself a 7715 RPC implementation and does not use 7710's `redeemDelegations`.
- Safe: no first-party 7715 or 7710 support found. Safe accounts can become 7710 delegators only by installing an executor module that exposes `executeFromExecutor` and trusts a DelegationManager. UNVERIFIED that anyone ships that.

Summary: exactly one stack (MetaMask) implements 7715 request plus 7710 redemption end to end on mainnets, and it is a close variant of the current ERC text. It is not letter-perfect. Everyone else has either a proprietary equivalent (Coinbase) or an experimental client against the old spec (Reown).

## 4. Honouring a 7715 grant natively on an EIP-8130 / EIP-8141 account

### The two proposals today

- EIP-8130 "Keystore Accounts" (Core, Draft, created 2025-10-14, Chris Hunter, Base; renamed 2026-09-03, scope bits realigned 2026-09-14, last edit 2026-09-16). A Keystore contract at `KEYSTORE_ADDRESS` stores per-account actors: `authenticator(20) || expiry(6) || scope(2)` per `actorId`. Scope bits: `OPERATOR 0x01`, `SELF_PAYER 0x02`, `SPONSOR_PAYER 0x04`, `POLICY 0x08`, `NONCE 0x10`; `0x0000` is admin. A `POLICY` actor without `OPERATOR` may only call `policy_manager(account, actorId)`, and the Keystore also stores a 32-byte `policy_commitment`. The protocol enforces the target check (`ActorPolicyViolation`); the manager contract enforces the actual limits by checking the presented parameters against the commitment. A tx-context precompile exposes `getTransactionSender`, `getTransactionPayer`, `getTransactionCalls`, `getTransactionSenderActorId`. Base runs this on a devnet.
- EIP-8141 "Frame Transaction" (Core, Draft, created 2026-01-29, Buterin, lightclient, Lange, Weiss, Forshtat, Tirosh, Nacson, Chiang, Wahrstätter, Vlachakis; last edit 2026-09-01). Tx type 0x06 with `frames = [[mode, flags, target, limits, value, data], ...]`, `VERIFY` frames run as staticcall and end with `APPROVE`, `SENDER` frames run as the account, `TXPARAM`/`FRAMEDATALOAD`/`SIGPARAM` opcodes for introspection, signature schemes `SECP256K1`, `P256`, `ARBITRARY`. Scheduled for Inclusion in Hegotá (2027) on 2026-08-27 and flagged must-ship by the EF in early September 2026. Note: 8130 and 8141 now compete; the joint effort to stack one on the other ended in 2026. A "keystore + frames" account is therefore a design exercise with no spec behind it.

### Mapping a 7715 grant

The clean mapping is: one 7715 permission = one Keystore actor with `POLICY` scope, whose `policy_manager` is a 7710-style manager and whose `policy_commitment` is the hash of the permission's terms.

Step by step:
1. Dapp calls `wallet_requestExecutionPermissions` with `to = session account`, a permission, and rules.
2. The wallet shows the terms. On approval it does not sign an EIP-712 Delegation; instead it emits a Keystore config change `AuthorizeActor` for the account: `actorId` = derived from the session account's key (for a `k1` or `p256` authenticator) or from the session account's address (a `delegate` authenticator, which 8130 lists as canonical), `scope = POLICY` (plus `SELF_PAYER` if the user pays gas, or none if the dapp sponsors), `expiry` = the 7715 expiry rule, `policyData = manager(20) || keccak256(permission terms)(32)`.
3. The response's `context` encodes `(account, actorId, the plaintext terms)`; `delegationManager` is the manager address stored in `policy_manager`.
4. To redeem, the session account sends an 8130 AA tx with `sender = user account`, `sender_auth = authenticator || sessionSig`, and `calls = [[{to: manager, data: redeemDelegations([context], [mode], [exec])}]]`. The protocol checks `call.to == policy_manager`; the manager recomputes `keccak256(terms)`, compares it with `policy_commitment(account, actorId)` read from the Keystore, runs the caveat logic (periodic budget, stream rate, allowlist), and then performs the execution from the account.
5. Revocation (`wallet_revokeExecutionPermission`) = `RevokeActor`, which deletes the slot. The protocol enforces the expiry itself, so no enforcer contract is involved.

What this buys over the 7710 reference: the session key is a first-class protocol key, gas can be self-paid or sponsored through the same tx, there is no `isValidSignature` round trip and no executor-module trust, and the target restriction is consensus-enforced before any contract code runs.

On 8141 the equivalent is: a `VERIFY` frame whose code checks the session signature (via `SIGPARAM` for P256/secp256k1 or `SIGDATACOPY` for arbitrary) against a stored session record and inspects the pending `SENDER` frames with `FRAMEPARAM`/`FRAMEDATALOAD` before calling `APPROVE`. The permission store and the policy check both live in account code; there is no Keystore or policy_manager concept in 8141 itself.

### Where the ERCs would need extending

- 7715 response: add a native-account variant. Today the response assumes `delegationManager` plus an opaque `context`. A keystore grant needs to expose `actorId`, the authenticator, and the account's `KEYSTORE_ADDRESS` so the session account can construct an 8130 tx. Simplest form: keep `delegationManager` as the policy manager and add an optional `session: { actorId, authenticator, scope, expiry }` object. Likewise a permission or rule type such as `keystore-session` (or reuse `expiry` as the actor expiry) so wallets can advertise it via `wallet_getSupportedExecutionPermissions`.
- 7715 signer model: the current text dropped signer types entirely; `to` is always an address. For a keystore actor the wallet needs a public key or an authenticator id on top of the address, unless it uses the 8130 `delegate` authenticator (address-based). The old spec's `key` / `keys` signers would fit better here; a small extension ERC could reintroduce `signer` as optional.
- 7710 manager as a policy manager: `redeemDelegations` takes the authority proof in calldata. On 8130 the authority is already proved by `sender_auth`, so the manager should accept a context that carries terms only and verify them against `policy_commitment` via the Keystore, and should read the actor with `getTransactionSenderActorId()` instead of trusting `msg.sender`. That is a new manager implementation and leaves the 7710 interface as it is, but 7710 would need a note that `_permissionContexts` may carry "terms + commitment reference" in place of a "signed delegation chain".
- Execution path: 7710's reference calls `executeFromExecutor` on the delegator. Under 8130 the calls run as the account already, so the manager either becomes the account's own module (called by the account during the AA tx) or the wallet sets `policy_manager` to the account itself, which 8130 forbids at creation (`manager = account` is disallowed in the create entry) and which the spec leaves UNVERIFIED for later config changes. This needs a decision in the 8130 text.
- Caveat enforcer hooks: `ICaveatEnforcer` hooks receive `_delegator` and `_redeemer`. In an 8130 tx the redeemer is the account's own actor, so enforcers keyed on redeemer address (for example per-delegate budgets) need to key on `actorId` instead. Extension: pass `bytes32 actorId` or hash it into `_delegationHash`.
- Dependencies: 7715's `dependencies` (factory + factoryData) assume ERC-4337 deployment. An 8130 account is deployed by a `Create` entry in the same tx, so a native variant would replace `dependencies` with the create entry's `user_salt`, `code`, and `initial_actors`.
- Nothing in 8130 or 8141 mentions 7710, 7715, or 7579. Alignment would happen in an ERC; the core EIPs stay untouched.
