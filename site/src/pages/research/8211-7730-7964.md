## 1. ERC-8211: Smart Batching

### Identity

- Title: "Smart Batching". Verified in the PR preamble and on erc8211.com.
- Status: Draft. Requires: ERC-7964.
- eips.ethereum.org/EIPS/eip-8211 returns 404 and so does ercs.ethereum.org/ERCS/erc-8211 and the raw master file. The number 8211 is assigned but the file has not merged. The PR "Add ERC: Smart Batching" is open, with one non-editor approval and comments from lightclient, abcoathup, ernestognw, forshtat and andrewhong5297. PR page says it is "awaiting additional editor reviews".
- Dates are inconsistent across sources: preamble says created 2026-02-11, eco.com says the PR opened 2026-02-11, GitHub shows PR activity from 2026-03-30, the Magicians thread was opened 2026-04-02, erc8211.com and press coverage say "published April 6, 2026". Use 2026-02-11 as the created date and treat the April dates as the public announcement.
- Joint Biconomy and Ethereum Foundation project. Reference implementation: github.com/bcnmy/composable-batch-erc. SDK: `@biconomy/smart-batching` (npm), announced 2026-05-26.

### The one-line idea

A normal batch freezes every argument at signing time. An 8211 batch lets each argument say "compute me at execution time from chain state, and revert unless I satisfy these bounds". That is the whole standard: a wire format for batches whose parameters are fetched and checked on-chain, plus a small execution algorithm every conforming account must follow.

### Exact structures (from the PR diff)

Interface:

```solidity
interface IComposableExecution {
    function executeComposable(ComposableExecution[] calldata executions) external payable;
}
```

One batch entry:

```solidity
struct ComposableExecution {
    bytes4 functionSig;          // selector the call starts with
    InputParam[] inputParams;    // how to build target, value, calldata
    OutputParam[] outputParams;  // what to capture after the call
}
```

Inputs:

```solidity
struct InputParam {
    InputParamType paramType;          // TARGET | VALUE | CALL_DATA
    InputParamFetcherType fetcherType; // RAW_BYTES | STATIC_CALL | BALANCE
    bytes paramData;                   // fetcher-specific
    Constraint[] constraints;          // checks on the resolved value
}
```

- `InputParamType`: `TARGET` (resolved value becomes the call target address), `VALUE` (becomes msg.value forwarded), `CALL_DATA` (appended to the calldata being built).
- `InputParamFetcherType`:
  - `RAW_BYTES`: `paramData` is used as-is.
  - `STATIC_CALL`: `paramData = abi.encode(address contractAddr, bytes callData)`; the implementation does a `staticcall` and uses the return data.
  - `BALANCE`: `paramData = abi.encodePacked(address token, address account)` (40 bytes). `token == address(0)` means native balance, otherwise `IERC20(token).balanceOf(account)`.

Constraints:

```solidity
struct Constraint { ConstraintType constraintType; bytes referenceData; }
enum ConstraintType { EQ, GTE, LTE, IN }   // IN = lowerBound <= value <= upperBound
```

Constraints compare as `bytes32`, so they work on uint256, address and other 32-byte types. Reviewers on the PR flagged that this is unsigned-only and that dynamic return types (bytes, string, arrays) need helper contracts to unwrap offsets. The Biconomy SDK and the v2.2.2 audit scope mention `signedGte`/`signedLte`, `IN_SIGNED`, `OR` composition and `SKIP`. Those exist in Biconomy's implementation but I could not confirm they are in the current PR text. UNVERIFIED whether the spec text has been updated to include signed and OR constraints.

Outputs:

```solidity
struct OutputParam { OutputParamFetcherType fetcherType; bytes paramData; }
enum OutputParamFetcherType { EXEC_RESULT, STATIC_CALL }
```

- `EXEC_RESULT`: `paramData = abi.encode(uint256 returnValueCount, address storageContract, bytes32 storageSlot)`. Takes `returnValueCount` 32-byte words from the call's return data and writes them to the Storage contract at slots derived from `storageSlot`.
- `STATIC_CALL`: `paramData = abi.encode(uint256 returnValueCount, address sourceContract, bytes sourceCallData, address storageContract, bytes32 storageSlot)`. Does a staticcall after the call and stores the result.

Storage contract:

```solidity
contract Storage {
    function writeStorage(bytes32 slot, bytes32 value, address account) external;
    function readStorage(bytes32 namespace, bytes32 slot) external view returns (bytes32);
    function getNamespace(address account, address caller) public pure returns (bytes32);
    function getNamespacedSlot(bytes32 namespace, bytes32 slot) public pure returns (bytes32);
    function isSlotInitialized(bytes32 namespace, bytes32 slot) external view returns (bool);
}
```

`namespace = keccak256(abi.encodePacked(account, caller))`, `namespacedSlot = keccak256(abi.encodePacked(namespace, slot))`. Implementations MAY use EIP-1153 transient storage.

### How one call's output feeds the next

There are two mechanisms, and the spec says which one to prefer.

1. Storage round-trip. Step N has an `EXEC_RESULT` output param that writes return words into Storage. Step N+1 has an input param with `fetcherType = STATIC_CALL` whose calldata is `Storage.readStorage(namespace, slot)`. The value comes back as bytes and is routed to `CALL_DATA`, `VALUE` or `TARGET`.
2. Re-read side effects. The spec says the "preferred pattern" is not to store anything: step N+1 just uses a `BALANCE` fetcher (or a `STATIC_CALL` to a getter) to observe what step N did. Swap then `supply(BALANCE(USDC))` is the canonical example.

There is no DSL and no opcode set. The "instructions" are the three fetcher enums, the three routing enums, the four constraint enums and the two output fetchers. Biconomy's own Weiroll comparison (2026-04-15) makes the point explicitly: Weiroll is a small VM with packed bytes32 commands, 8211 is self-describing structured data with no branching, no loops and no arbitrary writes. The authors call the restriction deliberate: fetch, constrain, route, call, in order, and nothing else, so wallets and explorers can render it.

### Execution algorithm (normative)

For each entry: set `target = address(0)`, `value = 0`, `calldata = functionSig`. For each input param: resolve via fetcher, check every constraint (revert the whole batch on failure), route the value. If `target != address(0)` do `target.call{value: value}(calldata)`. Then run output params. Any failed staticcall reverts the whole batch. Implementations MUST forward `msg.value` correctly and SHOULD have a reentrancy guard.

### Predicate entries

An entry with no `TARGET` input param is a predicate: constraints are evaluated, no call is made. Requirements: no TARGET param, one or more `CALL_DATA` params with `STATIC_CALL` or `BALANCE` fetchers carrying constraints, empty `outputParams`. Intended use: a relayer simulates with `eth_call`, and if the predicate reverts it waits and retries. This is how "sign now, execute when the bridge lands" works.

### Cross-chain

The spec requires ERC-7964. One EIP-712 signature (chainId omitted from the domain) covers an array of per-chain operations; each chain's batch opens with a predicate entry gating on the previous chain's effect (balance >= threshold, nonce, timestamp). The spec says orchestration is agnostic to the bridge (native bridge, ERC-7683 intents, ERC-7786 messaging): the predicate only observes the resulting state. The PR history shows Merkle-root authorization was replaced by ERC-7964 after reviewer feedback; the April Weiroll article still mentions Merkle roots, so that text is stale.

### Account integration

Encoding-first: the same bytes are consumed by an ERC-7579 executor/fallback module, an ERC-6900 plugin, a native account implementation, or an EIP-7702 delegation target. A gist by the lead author (2026-05-08) maps 8211 onto EIP-8141 frame transactions: each `ComposableExecution` becomes its own `SENDER` frame calling `executeComposable([entry_i])`, with the `ATOMIC_BATCH_FLAG` set on all but the last frame; a "Read Aggregator" view module on the account replaces the external Storage contract. That is a design note. It is not part of the ERC.

### Production status on Biconomy Nexus

Verified from docs.biconomy.io/contracts-and-audits:

- Nexus v2.2.3 (Nexus 1.3.3) is the current production release and "bundles the audited ERC-8211 Smart Batching reference implementation". Recommended for new accounts.
- Deployed addresses: Composable Execution Module `0x0000821108B5C9F3fe17E40811bE5b66DaF8f0e7`, Composable Storage `0x00008211dea1Aca67ac55fc44AE3bF88CF41281d`.
- Audits: Zenith (March 2025) and Pashov (March 2025) on the earlier composability stack; Pashov Audit Group (May 2026) on the ERC-8211 submodule pinned in v2.2.2 (signed constraints, IN_SIGNED, OR composition, SKIP, pipeline hardening).
- Biconomy's blog says the pattern (their MEE, Modular Execution Environment) has run in production "for over a year" as of May 2026. The ERC text itself is Draft. Chains where the module is deployed are not listed on the page I read. UNVERIFIED which chains.

Security notes from the spec worth repeating: storage slot derivation must include the account address; call vs delegatecall context changes which storage the adapter sees; runtime values can be manipulated in-block (flash loans, sandwiches), so constraint bounds matter; relayers cannot forge constraint results because they are evaluated on-chain.

## 2. ERC-7730: Structured Data Clear Signing Format

### Identity and status

- Status: Draft on eips.ethereum.org. Requires EIP-155, EIP-712. Created 2024-02-07.
- Governance moved from Ledger to the Ethereum Foundation's Trillion Dollar Security initiative on 2026-05-12. The EF now hosts the registry (github.com/ethereum/clear-signing-erc7730-registry) and the site clearsigning.org. Ledger Donjon still does independent audits.
- Schema versions: `1.0.0` deprecated, `2.0.0` active (`erc7730-v2.schema.json`), `3.0.0-next` in draft. Registry PRs must validate against v2 and include `testsv2/` cases.

### Descriptor format

A descriptor is one JSON file per contract (files named `calldata-*.json`) or per EIP-712 message family (`eip712-*.json`). Top-level keys: `$schema`, optional `includes`, `context`, `metadata`, `display`.

`context` binds the file to data:
- `contract`: `deployments` (array of `{chainId, address}`), optional `factory` (`deployEvent`, `deployments`) for multi-instance contracts, plus the ABI or a reference to it.
- `eip712`: `domain` key-values, `deployments`, or a `domainSeparator`, plus the message schemas.
- `$id`: human-readable name.

`metadata`: constants in scope of the contract. `owner`, `contractName`, `info` (`deploymentDate`, `url`), `token` (name/ticker/decimals for non-standard tokens), `constants` (referenced as `$.metadata.constants.X`), `maps` (`$keyType`, `values`), `enums`.

`display`:
- `definitions`: reusable field formats, referenced as `$.display.definitions.NAME`.
- `formats`: keyed by function signature (calldata) or primary type (EIP-712). Each entry has:
  - `intent`: a string ("Swap") or an object of label/value pairs.
  - `interpolatedIntent`: a template with `{path}` placeholders, formatted with the field rules. `{{` escapes a brace.
  - `fields`: ordered array of field formats, `$ref`s to definitions, or groups.
  - `required`, `excluded` (lists of paths that must be shown or are deliberately hidden). Present in the schema; their exact text was not re-read on the page. UNVERIFIED wording.

A field has `path` (or literal `value`), `label`, `format`, `params`, optional `visible` (`always` / `never` / `optional` / rules with `ifNotIn`, `mustMatch`), `separator` for arrays, and `encryption` (`scheme` such as `fhevm`, `plaintextType`, `fallbackLabel`).

Formats by ABI type:
- int/uint: `raw`, `amount` (native currency), `tokenAmount` (params `tokenPath`/`token`, `nativeCurrencyAddress`, `threshold`, `message`, `chainIdPath`/`chainId`), `nftName`, `date`, `duration`, `unit` (`base`, `decimals`, `prefix`), `enum`, `chainId`.
- string: `raw`.
- bytes: `raw`, `calldata` (params `calleePath`/`callee`, `selectorPath`/`selector`, `chainIdPath`/`chainId`, `amountPath`/`amount`, `spenderPath`/`spender`).
- address: `raw` (ERC-55), `addressName` (`types`: eoa/contract/token/collection/wallet; `sources`: ens/local; `senderAddress`), `tokenTicker`, `interoperableAddressName` (ERC-7930).

Paths: `#` = the decoded structured data, `$` = the merged descriptor, `@` = the container (`@.from`, `@.to`, `@.value`, `@.chainId`). Slices like `#.data.[0:20]`, `#.array.[-1]`, `#.details.[]`. Groups have `path`, `label`, `iteration` (`sequential` or `bundled`) and nested `fields`.

### Registry

github.com/ethereum/clear-signing-erc7730-registry. Layout: `specs/` (v1, v2, test schemas), `registry/<entity>/` (descriptors, `testsv2/`, auditor signatures), `ercs/` (ERC-20, ERC-721 and similar generic descriptors), `tools/`. ### How it applies to frames and batches, and where the gaps are

What the spec says today:
- EIP-5792 batches: wallets SHOULD either concatenate each call's `interpolatedIntent` with " and " into one sentence ("Approve DEX Router ... and Swap ... and Mint"), or show one intent screen per call with clear separation.
- ERC-4337: a `PackedUserOperation` EIP-712 descriptor exists (`example-userops-eip712.json`); the inner `execute` calldata is resolved through the account's own descriptor (`example-account-execute.json`) and then the target contract's descriptor via the `calldata` format. Each smart-account implementation needs its own descriptor because `execute` is implementation-specific.
- Nested calls: the `calldata` format with `callee`/`selector` is the recursion primitive. The Magicians thread calls multicall support "experimental" and notes hardware-screen limits.
- Not covered in the spec text: EIP-7702 delegation context, EIP-8141 frames, ERC-8211 fetchers. The Magicians thread (May 2026) discusses adding a 7702 "delegation context", an "intent mutability" field that tracks storage slots so a wallet can detect proxy upgrades, signer attestations, and ERC-8265 (prepared transaction envelope) for offline wallets. None of that is in the published Draft.

Gaps for a native-AA account:
1. Descriptors are per contract call. There is no descriptor type for "a batch" as a unit, no way to express a whole-batch invariant ("net USDC out \<= X"), and no way to describe the relationship between calls. The " and " concatenation rule is the only batch-level guidance.
2. Runtime-resolved arguments (8211 `BALANCE`, `STATIC_CALL`) have no representation. A 7730 field assumes the value is in the calldata. A predicate entry (no target) has no matching format at all.
3. Frames (8141) have no container binding. `@.from`, `@.to`, `@.value`, `@.chainId` describe one transaction; a frame transaction has several frames with different targets and a verification frame that is not a user call.
4. Keystore / account-management operations (add key, set spend limit, rotate signer) are just calls on the account contract, so they need the account vendor to publish its own `calldata-*.json`. There is no generic "account operation" descriptor family. The 4337 example shows the same thing: each account implementation ships its own file.
5. Cross-chain: 7964 messages are plain EIP-712, so a 7730 `eip712` descriptor could be written for a `CrossChainIntent` type, but the descriptor would have to be per application and chainId is inside each array element, so it is absent from the domain. No worked example exists. UNVERIFIED that anyone has published one.

## 3. ERC-7964: Crosschain EIP-712 Signatures

### Identity

- Title: "Crosschain EIP-712 Signatures". Status Draft. Created 2025-06-05. Author Ernesto Garcia (OpenZeppelin). Requires EIP-712, ERC-1271, ERC-5267. Published on eips.ethereum.org (the number is an ERC, the URL path is /EIPS/eip-7964).
- History: original draft used `chainId: 0`; rework on 2025-12-01 switched to omitting `chainId` entirely because EIP-712 domain fields are all optional. Demo at erc7964-demo.vercel.app (Sepolia, Arbitrum Sepolia, Base Sepolia), updated 2026-05-28. The reference implementation exposes `CrossChainSignatureChecker.isValidCrossChainSignatureNowCalldata(...)`. It is not in the OpenZeppelin community-contracts crosschain docs I checked. UNVERIFIED whether it ships in any OpenZeppelin package.

### What it standardizes

One EIP-712 signature that is valid on several chains, using nothing but standard EIP-712 so any wallet displays the full content.

1. Domain: omit `chainId` from `EIP712Domain`. Normally only `name` and `version` remain; `verifyingContract` may stay if the app is at the same address on every chain.
2. Message: the primary struct contains an array of per-chain operation structs. Each element MUST carry a field named exactly `chainId` (first one found by depth-first, insertion-order traversal is canonical), and, unless the domain has `verifyingContract`, a per-chain `verifyingContract` or equivalent. The spec suggests a nested struct like `EIP712ChainDomain(uint256 chainId,address verifyingContract)`.
3. Hashing: standard EIP-712 array encoding. The array hashes to `keccak256(abi.encodePacked(structHash[0] ‖ ... ‖ structHash[n]))`. Example:

```
CrossChainIntent(ChainOperation[] operations,uint256 nonce,uint256 deadline)
ChainOperation(EIP712ChainDomain domain,address target,uint256 value,bytes data)
EIP712ChainDomain(uint256 chainId,address verifyingContract)
```

4. On-chain envelope. The signature bytes handed to `isValidSignature` or an ECDSA check are `abi.encode(bytes32 header, bytes32[] structsArray, bytes crossChainSignature)` where `header = abi.encodePacked(magic, fields, structIndex, application)`:
   - `magic`: 9 bytes `0x796479647964796479`
   - `fields`: 1 byte, ERC-5267 domain-fields bitmap
   - `structIndex`: uint16, which element of `structsArray` is this chain's
   - `application`: 20-byte address of a contract implementing ERC-5267 `eip712Domain()`
   - `structsArray`: one bytes32 struct hash per chain
   - `crossChainSignature`: the real signature.
5. Verification: detect the magic prefix, check `structsArray[structIndex]` equals the struct hash recomputed from this chain's full operation data, fetch the domain from `application`, rebuild the top-level hash from the domain, the full-message typehash and the array hash, verify the signature. Each chain only needs its own full operation plus the other chains' hashes (N x 32 bytes).

Rationale highlights: arrays instead of Merkle trees because standard wallets can display arrays but cannot verify Merkle leaves; for 2-5 chains the calldata saving of Merkle proofs is 32-64 bytes. Omitting `chainId` beats `chainId = 0` because it is a clear signal and works with unmodified wallets.

Security: replay across chains is the point, so nonces and deadlines must live inside the message; check the account exists on this chain (ERC-6492 for counterfactual accounts); code and state can diverge per chain; no atomicity, so partial execution and out-of-order execution are possible; domain upgrades on one chain invalidate outstanding signatures only there.

### How a shared account core would use it for "native cross-chain" operations

- Define one primary type (say `CrossChainIntent`) with `operations[]`, `nonce`, `deadline`. Each operation carries `chainId`, optionally `verifyingContract`, and the payload for that chain (for an 8211 account, the encoded `ComposableExecution[]` for that chain, or its hash).
- The user signs once. The wallet shows every chain's operations because it is ordinary typed data.
- On each chain the account (or its validator module) receives the 7964 envelope, recomputes its own operation's struct hash, checks it is at `structIndex`, rebuilds the domain from an ERC-5267 contract deployed at the same address everywhere, and verifies.
- This is exactly the dependency ERC-8211 declares: 8211 predicates make the per-chain batches order-tolerant ("wait until the bridge landed"), and 7964 makes one signature cover all of them. Under EIP-8141 the per-chain batch would be delivered as frames; the gist maps each 8211 entry to a `SENDER` frame.
- The account has to supply replay protection per chain in the message (nonce per chain, or a nonce plus the chainId already in the struct) and should include a `deadline`.
